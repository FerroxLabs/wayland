## 4. THE NEXT PIECE OF WORK: making voice conversational

This came out of Sean using it and is not yet built. Read this section before touching voice.

**What happened.** He tapped the orb, asked it to check the system, and it **read a markdown answer
aloud** — bullet lists, file paths, version strings ("Vercel CLI is 53.1.0, current is 58.9.4").
Correct on screen, unbearable in the ear.

**The diagnosis.** One output is serving two channels. Everything that makes a response good to read
makes it bad to hear. ChatGPT feels different partly because its voice mode is **speech-to-speech** —
audio in, audio out, no text in the middle. Their *old* pipeline was our shape and had our problem.

**Sean's own objection killed the obvious fix, and he was right.** If you instruct the agent to
answer conversationally in voice mode, those vague turns become the conversation history — so
switching back to text leaves the model pattern-matching on its own vague prior turns, and the
transcript has permanently lost the detail. **Never change what the agent writes.**

**The next candidate — derive a spoken summary from the finished answer — he also correctly
rejected.** It makes latency *worse* (generate, then summarise, then synthesise) and latency is most
of what "conversational" means. It is a legibility fix, not a conversation fix.

**Where the discussion landed, and Sean confirmed the goal.** Asked whether voice is for *talking
and thinking out loud* or for *driving real work hands-free*, he said: **the first.**

That reframes it entirely: **voice mode should not be the coding agent at all.** He tapped the orb
and got a CLI agent doing a system check because that is what it is. A task-executor cannot be made
conversational by phrasing — "receive task, work, report" is a monologue shape.

**Recommended shape, cheapest path that actually addresses the goal:**
- **A conversational persona, not the coding agent.** The voice session already runs an assistant —
  his showed `Concierge · Permission: Ask` — so the persona layer exists. Make that assistant an
  actual conversationalist: short turns, no markdown, no paths or versions, asks back, and hands off
  to the coding agent only when real work is requested.
- **A fast model, not Opus.** "How's it going, what do you reckon" wants half a second, not twenty.
- **Speak the first sentence while the rest still generates.** Biggest single lever on perceived
  latency. Today we wait for the whole answer, then synthesise, then play.
- **Barge-in.** Talk over it, it stops and listens, pending generation cancelled. Nothing feels more
  machine-like than being unable to interrupt.

**The blocking unknown, and the first thing to establish:** can voice mode pin its **own assistant
and model**, independently of whatever the chat tab is set to? If tapping the orb inherits Claude
Code because the chat was on Claude Code, the persona fix does not hold and that is the first thing
to change. **This has not been checked.**

**The bigger alternative, for the record:** a speech-native realtime model handling conversation with
the coding agent available to it *as a tool*. That is what ChatGPT actually does and it would beat
the above — but it needs a hosted realtime audio key, which cuts against "works with no keys out of
the box."

**Also still open from earlier and unresolved:** kokoro was deleted (correctly — its binary resolver
returned null unconditionally and it needed a runtime, a 28 MB voices file and a phonemiser that
exist nowhere in the codebase). But that leaves macOS `say` as the local speech-out floor, which is
the system voice Sean already said is not good enough. **We removed a broken option without shipping
a better one.** Choosing a proper on-device TTS with a shippable licence is a real open decision.

## 9. LATE UPDATE: the Claude Code bridge failure, root-caused properly

`packet/wl-integration` is now **`b301e1c91`**, 17,351 passed / 2 failed (both the same known
`constitutionReclaimNotice` timing flake, which took two tests with it under load; the file passes
4/4 in isolation). Supersedes the head and suite numbers in section 1. All agents are finished.

**My framing in section 6 was wrong.** I said "nothing detected, retried or self-healed". Recovery
code existed in two places. Both were dead, for different reasons, and a fifth problem meant the app
never even got as far as failing. All five established by execution:

1. **`waitForSpawn` never settles if `spawn` fires before its listener attaches.** Node sets
   `child.pid` synchronously inside `spawn()` but emits `'spawn'` on the **next tick**, so any
   `await` between the two loses the event permanently and `ProcessAcpClient.start()` hangs forever:
   no error, no timeout, nothing to retry. **This is why the backend went silent rather than
   erroring**, and it reproduces deterministically on the second spawn of a retried start.
2. **The cleanup refused to delete the broken directory.** `isInsideBunCleanupRoot` compared
   `path.resolve(os.tmpdir())` (`/var/folders/.../T`) against the path bun prints
   (`/private/var/folders/.../T`). Same directory, two spellings; `startsWith` says no, so it logged
   "Refusing to clear suspicious cache path" and left the corruption in place.
3. The cleanup was bound to `this._client`, which `clearClient()` has already nulled by the time it
   runs.
4. A disconnect during `initialize` discarded the stderr, so whichever lifecycle signal landed first
   decided the error type - producing exactly the bare `Agent disconnected (connection_close, code:
   null)` on screen while the module error was thrown away.
5. **`acpConnectors.ts`'s bunx recovery is unreachable** (reported, deliberately not changed):
   `spawnViaNpxHooks` resolves `setup()` immediately after spawn and its body has no throw path, so
   `connectNpxBackend`'s catch can only ever see a synchronous `spawn()` failure.
   `isBunxCacheCorruption` / `clearBunxCache` cannot fire for a bridge crash. **Their tests pass
   because they call the functions directly** - the fabricated-fixture trap, for the sixth time.

Recovery is now one shot: clear the install, retry once, stop. Errors that are not this class keep
their existing retry budget. A startup crash carrying a module error but no clearable install now
goes terminal immediately rather than burning three futile retries.

**The `(bundled bun)` log label was a lie, and my suspicion about it was right.**
`resources/bundled-bun/` does not exist in a dev build, `resolveNpxPath` silently falls back to bare
`bun` off PATH, and the log line hard-coded "bundled bun". Sean's machine ran system bun 1.3.11
while the log said otherwise. Now reports the label **and** the resolved command. This matters
beyond tidiness: openclaw was cut from the install band specifically because it fails under bundled
bun, so runtime-selection logs have to be trustworthy.

**Open, flagged rather than decided:** process-side ACP error prose has **no keyed i18n path at
all**. These banners are plain English rendered verbatim, as are their siblings
(`buildAcpSetupGuidance`, `AcpAgentV2`'s auth message). Localizing them means building a
process-side translation pipeline for the whole class - a separate piece of work, not a line in this
one.

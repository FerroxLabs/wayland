## W-1 — Publication compare-and-set failure  🔴 BLOCKER

Everything else is cosmetic next to this. It is **not** TVControl-specific: it makes
enabling or reconnecting **any** connector unreliable, and a failure leaves the row in a
state the UI presents as unrecoverable.

### Observed behaviour (reproduced, logs in `/tmp/wl-run4.log`)

Reconnect on a disabled stdio connector:

```
09:49:15.863 [WCoreMcpAgent]   Added MCP server: tvcontrol
09:49:15.912 [WaylandMcpAgent] Installed MCP servers: tvcontrol
09:49:16.852 [GeminiMcpAgent]  Added MCP server: tvcontrol
09:49:34.264 [CodexMcpAgent]   Added MCP server: tvcontrol
09:49:36.311 [ClaudeMcpAgent]  Added MCP server: tvcontrol     <- all five succeed
09:50:22.078 ...               Removed MCP server: tvcontrol   <- rollback, 46s later
```

Publication succeeds everywhere, then the local commit fails and the rollback strips it
back out. Durable result: `status: error`, `lastError: "publication rollback incomplete —
reconnect this connector"`. Survives an app restart.

### ⚠️ Root cause is NOT established — do not skip to a fix

An earlier session attributed this to `refreshServerStatuses` racing the publication.
**That attribution is unproven and probably wrong**: its target filter
(`useMcpConnection.ts:459-466`) requires `s.enabled === true`, and the connector stays
`enabled: false` in durable storage for the whole publication window, because
`handleToggleMcpServer` publishes *before* it commits. It was never a candidate.

Two hypotheses remain. They need different fixes, so identify which one first.

**H1 — row-level guard.** `useMcpServerCRUD.ts:377-385`:

```js
await saveMcpServers((prevServers) => {
  committed = false;
  return prevServers.map((server) => {
    if (server.id !== serverId || server.updatedAt !== targetServer.updatedAt) return server;
    committed = true;
    return updatedTargetServer;
  });
});
if (!committed) throw new Error('MCP declaration changed while publication was in progress');
```

`targetServer.updatedAt` is read at t0 and compared at t0+45s. Any writer that bumps that
row's `updatedAt` in between makes `committed` false. Full writer list is 16 call sites —
`rg 'saveMcpServers\(' src/renderer`.

**H2 — global revision exhaustion.** `enqueueMcpConfigWrite`
(`useMcpServers.ts:35-61`) CASes on a **whole-config** `revision`, so a write to *any*
server invalidates a write to *every* server. It retries `MAX_MCP_CONFIG_CAS_ATTEMPTS = 16`
then throws `MCP config changed too frequently to commit safely` — which lands in the same
catch and produces the same rollback. Agent-detection sweeps run every few seconds during
publication, so sustained revision churn is plausible.

H1 and H2 are distinguishable by the thrown message alone.

### Phase A — diagnose (do this first, it is cheap)

1. Log every `enqueueMcpConfigWrite` entry: caller tag, attempt number, whether the CAS
   applied, and the target row's `updatedAt` before and after.
2. Reproduce: clean dev profile, add an stdio connector, click Reconnect, capture the log.
   Reproduction recipe is in `.planning/HANDOFF-2026-08-04-tvcontrol.md`.
3. **Deliverable: the named writer and the exact thrown message.** No fix lands before this.

Reproduction is reliable — it fired on every reconnect attempt across three runs, because
five serialized CLI agents take 20-45s to publish.

### Phase B — fix, per finding

- **If H1:** stop comparing a 45-second-old `updatedAt`. Re-read the row inside the updater
  and accept the commit when the declaration is materially unchanged, or move the row guard
  onto an identity that publication owns rather than one every writer bumps.
- **If H2:** the retry budget is not the fix — raise it and it still fails under load.
  Either scope the CAS to the row rather than the whole config, or serialize
  user-initiated publication against background writers.

Whichever it is, a **failed local commit after a fully successful publication must not be
reported as a rollback failure.** Publication succeeded; the correct recovery is to keep
it and re-commit, not to strip five agents and mark the row unrecoverable.

### Acceptance

- Enabling a connector whose publication takes >30s commits and does not roll back.
- Regression test in `tests/unit/useMcpServerCRUD.dom.test.tsx` (71 assertions already
  there): a slow `syncMcpToAgents` with a competing writer underneath it must still commit.
  **The test must fail against current `main`** — prove it before fixing.
- After a genuine publication failure, the row returns to a state the user can retry from.

}

function enqueueMcpConfigWrite(serversOrUpdater: IMcpServer[] | ((prev: IMcpServer[]) => IMcpServer[])): Promise<void> {
  const operation = mcpConfigWriteQueue.then(async () => {
    for (let attempt = 0; attempt < MAX_MCP_CONFIG_CAS_ATTEMPTS; attempt += 1) {
      // oxlint-disable-next-line no-await-in-loop -- every retry must observe the previous CAS result
      const persisted = await readMcpConfig();
      const next =
        typeof serversOrUpdater === 'function'
          ? serversOrUpdater(persisted.servers)
          : structuredClone(serversOrUpdater);
      // oxlint-disable-next-line no-await-in-loop -- CAS retries are intentionally serialized
      const response = await mcpService.compareAndSetMcpConfig.invoke({
        expectedRevision: persisted.revision,
        nextServers: next,
      });
      if (!response.success || !response.data) throw new Error(response.msg || 'Failed to write MCP config');
      if (!response.data.applied) continue;

      // Publish only the main-process-confirmed snapshot after persistence.
      // A rejected or conflicted write cannot manufacture renderer state.
      publishMcpConfig(response.data.snapshot.servers);
      return;
    }
    throw new Error('MCP config changed too frequently to commit safely');
  });
  mcpConfigWriteQueue = operation.catch((): void => undefined);
  return operation;
}

const hasPublicationDivergence = (server: Pick<IMcpServer, 'lastError'>): boolean =>
  typeof server.lastError === 'string' && server.lastError.includes(MCP_PUBLICATION_DIVERGENCE_MARKER);

export function retainMcpPublicationReconciliation(
  servers: IMcpServer[],
  serverId: string,
  fallback: IMcpServer
): IMcpServer[] {
  const exactIndex = servers.findIndex((candidate) => candidate.id === serverId);
  const canonicalIndex = servers.findIndex(
    (candidate) => mcpServerCollisionKey(candidate.name) === mcpServerCollisionKey(fallback.name)
  );
  const reconciliationIndex = exactIndex >= 0 ? exactIndex : canonicalIndex;
  const current = reconciliationIndex >= 0 ? servers[reconciliationIndex] : undefined;
  const reconciliationServer: IMcpServer = {
    ...(current ?? fallback),
    enabled: current?.enabled ?? false,
    status: 'error',
    lastError: MCP_PUBLICATION_DIVERGENCE_ERROR,
    updatedAt: nextMcpRevision((current ?? fallback).updatedAt),
  };

  if (reconciliationIndex < 0) return [...servers, reconciliationServer];
  const next = [...servers];
  next[reconciliationIndex] = reconciliationServer;
  return next;
}
